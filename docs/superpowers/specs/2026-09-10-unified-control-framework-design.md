# FastapiAdmin 统一中控与产品授权设计

日期：2026-09-10。状态：设计评审稿；已做本地源码和 Git 核查，未实施、未提交、未迁移数据库、未验证生产。

## 1. 目标与范围

将中控服务端、产品端接入、联邦用户授权和可靠同步统一维护在 FastapiAdmin 的主线中。支持独立 SaaS、中控、接入中控的产品三种装配，不使用长期分支区分产品版本。普通 SaaS 不依赖中控或 Celery Worker 即可登录并运行。

一期完整处理：企业产品开户、员工创建与选产品、授权同步、默认角色、产品登录、撤权、再次授权、失败重试和历史授权对账。保留产品自己的角色与业务数据。

一期不做：中控与所有产品共用一个数据库；全部业务请求经中控转发；通用跨产品业务事件平台；改换 RabbitMQ；把现有一次性启动码协议重写为 OIDC；Food 全业务代码搬入框架；自动部署或迁移生产。

一个源码仓库可以产生多个独立部署。中控与产品同进程、同库同时运行的组合装配不作为一期承诺，需要另行检验身份与数据所有权冲突。三种装配复用代码，不等于所有角色必须同时启用。

## 3. 方案选择

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 一个框架仓库，模块与装配分工 | 修复共用，单 SaaS 与中控版本一致 | 必须补齐模块关闭、依赖和迁移边界 | 采用 |
| 两个长期框架仓库 | 发布节奏独立 | 已出现修复分散和基础代码重复同步 | 不作为目标 |
| 一个进程、一个库承载所有产品 | 本地事务简单 | 改变现有独立产品的数据、权限和发布边界 | 一期不采用 |

参考依据：ABP 采用模块和可选认证宿主，Frappe 在框架内提供认证接入；这些模式说明代码组织和部署边界可以分开选择。此次具体实现以现有 Python 代码为基础，不照搬 .NET 的目录或引入新语言。

- https://docs.frappe.io/framework/oauth2

`saas-admin.toml` 和 `minimal.toml` 保持向后兼容；增加通用 `control.toml` 和 `federated-saas.toml` 示例。目标能力不得依赖装配名称是否恰好叫 control/food。

环境配置保留已有 `CONTROL_SSO_*`、`CONTROL_TENANT_PROVISIONING_ENABLED`、`CONTROL_USER_ACCESS_SYNC_ENABLED` 和 `CONTROL_USER_ACCESS_ENFORCEMENT_ENABLED`。Assembly 表示允许能力，运行配置表示是否配置启用；显式启用却缺少依赖时报错，不能悄悄变成弱校验。

## 5. 身份、Site、租户和应用边界

三类对象分别管理：

1. 中央身份：不可变 UUID，由中控维护；姓名和手机号不是跨系统关联主键。
2. 租户成员：同一用户在不同企业的成员及 owner/admin/member 关系，按租户分别判断。
3. 产品本地权限：产品租户下的角色、菜单、操作权限和数据范围。

每次启动、兑换、开户、授权同步、重试、对账和会话变更都校验 Site、应用绑定、中央租户到产品租户的映射。不同数据库的数值 ID 不互相等同。

实施核查修正：每个产品后端实例使用一个受信中控 issuer，可通过 CONTROL_SSO_SITE_CLIENTS 为不同 Site 配置不同客户端凭据；启用显式映射后未知 Site 拒绝回退。同一实例多 Site 的票据、租户与凭据必须一致匹配。多 issuer 联邦不在本期范围；application_code 是产品标识，与 client_id 分开。

同一用户属于多个租户时，撤销 A 的访问不得修改该用户全局状态或删除 B 的成员/角色/会话。产品内不得通过普通用户管理接口改写联邦身份字段或设置本地密码。

保护 owner/admin 治理角色及最后一个 owner；普通业务角色不得创建或提升成平台 superuser。框架保留受控本地应急管理员，但不允许中控载荷把普通联邦用户提升为 superuser。

## 6. 开用户与业务权限

用户流程：

1. 中控在 Site 下创建企业，并开通产品、配置目标套餐；产品端事务内建立租户和 owner。
2. 企业管理员创建员工，选择该企业已经开通的产品；创建员工不要求所有目标产品当时都在线。
3. 员工账号和每个产品的授权期望/任务原子持久化；网络调用在提交之后。
4. 每个产品独立接收授权，创建/复用影子用户、成员关系和访问资格。
5. 按产品声明补默认角色，已有有效产品角色则保留。
6. 中控只有在目标回执版本和状态匹配时才显示已生效；失败不回滚其他产品。
7. SSO 登录检查有效授权后签发产品本地会话。

默认角色抽象采用产品显式声明的策略，框架默认不自动授予业务权限。计划扩展 Assembly 的 `[federation.default_role]`，字段为 `mode = "manual" | "declared"`、`code`、`name`、`permission_codes`、`permission_prefixes`、`data_scope`。这是一项新契约，需由配置测试约束。

- 通用配置默认 manual；该模式允许有效访问资格但没有业务角色，用户进入明确的待授权页面。
- declared 模式需明确声明权限集合或产品权限命名空间；不能用空列表表达全部权限。
- 最终默认权限是声明范围 ∩ 租户套餐 ∩ 启用装配 ∩ 有效租户菜单。
- 系统管理、平台管理、中控管理等保留命名空间不能被默认角色声明重新放开。
- 数据范围默认仅本人。业务有不同需求时通过产品策略明确声明，不自动提为全部数据。
- Food 使用适配声明保持原有 USER 行为；框架通用模块不能导入 Food 的产品清单。
- 保留“无当前租户有效角色才补默认角色”的原有规则，同时明确：手动清空角色不等于撤销产品访问；要拒绝进入产品应执行撤权。
- 手工改成其他有效角色后，重新授权/重试/SSO 不覆盖角色；套餐变化则更新系统默认角色的权限上限。
- 治理角色和默认普通角色分别处理，不把 owner/admin 当成 USER。

## 7. 可靠同步与协议

复用 Food 链路：

```text
中控数据库：授权期望 + BusinessTask（同一事务）
  -> 提交后 Celery/Redis 派发；未派发任务可被扫描恢复
  -> Worker 获取当前绑定与权限，创建受限一次性同步码
  -> HTTP 调用产品 /system/auth/control/access/sync
  -> 产品向中控兑换码并校验绑定
  -> 产品数据库事务：访问资格 + 用户/角色 + 事件回执
  -> 中控核对应用结果版本，更新同步状态
```

沿用已有接口、字段和实际注册前缀；先用路由契约测试固定，再调整内部代码。不是新建一个无限用途的跨产品 RPC 系统。

中控事实：`desired_state`、`sync_status`、单调递增 `sync_version`、`last_event_id`、执行令牌、错误及重试记录。产品事实：`status`、`applied_version`、`last_event_id`、事件指纹/原始回执和 `session_cleanup_pending`。

规则：旧版本不得覆盖新版本；同事件同请求返回已保存结果；同版本不同事件或不匹配指纹返回冲突；旧任务完成不能覆盖较新中控状态；每次实际执行重新检查执行人和域权限。

出站地址来自管理员登记的应用配置，固定路径并限制协议/目标；不能将用户提交的任意 URL 当作同步目标。一次性码、客户端密钥和本地 session 不进入操作日志、任务明文载荷或错误摘要。区分 OAuth/OIDC 通用标准与本项目内部启动码协议，文档不得把后者描述为已实现完整 OIDC。

## 8. 撤权与故障语义

撤权分两个时点：

- 中控提交 inactive 后，立即阻止新的门户启动；界面显示撤权同步中。
- 产品应用 inactive 后，受保护的新请求拒绝；会话清理完成后中控才按回执显示完成。清理失败保留补偿状态，不回滚已提交的数据库撤权。

无法到达产品时，已有本地访问资格不能瞬间变化。本期采用可观测的最终一致性，不承诺网络分区下零延迟撤权，也不让每次业务请求同步访问中控。停用用户、移除成员、停用租户/应用/产品开通关系必须触发对应授权失效任务；范围操作需要可恢复的批处理。

如以后要求网络分区期间也必须在固定时间内撤权，需要另外引入授权有效期/续租策略并接受中控离线时用户被拒绝的可用性代价；本期不静默引入此行为。

覆盖登录、刷新、退出、切换租户、在线用户删除、WebSocket/SSE 流式会话。对已开始的普通业务事务不承诺回滚；长连接应在撤权后终止或停止后续受保护输出，并通过专门测试验证。

Redis 异常时不能把受保护的会话变更当成功；先保证产品数据库拒绝访问，再有界清理。恢复扫描应限批、限时、可续跑、持有正确锁，不能全库 KEYS 或无限循环。

## 9. 数据库与历史升级

仍使用一个中控库和各产品独立库；数据库数量不由仓库数量决定。框架所有部署使用同一套核心模型，但各实例只保存自己的业务数据。

原框架与原中控的基础迁移图可以保留 revision 和父节点，形成包含 `20260812_02` 的共同基础。Food 的两个 `20260831_01` 绝不能同时进入统一迁移目录。

新的统一框架使用唯一 revision：计划为 `20260910_fa_access` 和 `20260910_fa_control_access`（长度均不超过默认版本字段容量），分别承载产品访问账本和中控同步账本；执行前检查 ID 尚未占用。迁移按真实基础 head 串联，不依赖任何追溯/配送/冷链业务 revision。

一期正式支持新库、原 FastapiAdmin 库、原 FastapiAdmin-Control 库升级。Food 现有库本期保持自己的迁移链与 revision，不改写已应用迁移；先验证协议兼容，再单独制作下游桥接迁移计划。不能用修改旧 revision、直接 stamp head 或跳过 SQL 的方式伪装兼容。

旧授权启用强制检查的顺序：接收端/schema 就绪 -> 中控同步任务可运行 -> 基于中控真实授权和合法租户映射回填 -> 对账和异常处理 -> 确认无未解析存量后启用强制检查。不能为所有影子账号直接补 active。

遇到已存在但定义不同的表/约束时失败并报告差异，不能 create-if-not-exists 后跳过校验。回填必须 dry-run、明确目标、计数、幂等与限批；不得删除原角色及用户。

## 10. 发布与回滚

执行开发时可使用短期任务分支隔离并保留原始来源，最终回到同一主线，不保留 control 作为长期分叉。仅执行本次用户另行授权的提交/合并/推送操作。

代码发布顺序：产品端先支持协议和兼容开关，再更新中控发送端；对账后启用强制检查。不能让中控先把尚不支持新协议的产品记为已同步。

代码回滚优先保留新增表与账本，暂停新任务，使用兼容版本；不得因回滚直接关闭已启用的强制检查，使已撤权用户重新可用。需要恢复备份时明确备份时点、后续写入恢复和授权变更补偿。暂停派发不撤销已发送任务，恢复时继续按版本拒绝旧状态。

原 Control 目录、旧分支和 Food 源码在整合验收前保留。源记录使用 Git SHA 和文件映射追踪；不依赖以后还能从对话找回修复。

## 11. 验收口径

默认执行定向 pytest、Vitest、类型和静态检查。不启动浏览器、本地页面服务、全量测试或完整构建；这些只有用户明确要求时执行。数据库竞态测试必须在隔离 PostgreSQL/Redis 上运行，SQLite 成功不能代替真实锁语义；没有环境则保留未通过门禁，不能宣称完成运行验收。

必须证明三种装配、双 Site、双租户、至少两个通用示例产品下：开户、普通用户默认权限、人工角色保持、租户切换、重复/乱序同步、撤权/恢复、失联重试、旧账本回填均满足本文规则。至少一个样例不使用 Food 名称和权限前缀，以证明通用化。

代码通过不等于 Food 生产升级完成；生产数据库、真实 Worker、浏览器和跨网络联调分别列出证据。
