# 联邦用户本地授权闭环设计

## 1. 背景

FastapiAdmin 已支持中控签发一次性启动码、目标系统兑换启动码，以及在目标系统按需创建联邦影子账号。首次登录生成的账号只有目标租户成员关系，不自动获得目标系统部门、岗位、角色或菜单权限。当前等待页能够阻止无权限账号进入，但管理员缺少明确的待授权识别、筛选和处理入口。

本设计完善目标系统内的授权闭环。稳定性优先，复用现有用户管理和编辑流程，不同步中控组织或角色，不增加第二套用户管理页面。

## 2. 已确认的边界

### 2.1 数据归属

- 中控负责统一账号、租户身份、应用开通和用户应用准入。
- 每个业务系统独立负责本系统的部门、岗位、角色、菜单权限和数据权限。
- SSO 只同步身份资料和租户成员关系，不同步中控部门、中控角色或中控菜单权限。
- 联邦用户首次进入目标系统时仍不自动分配默认角色。

### 2.2 授权状态

“待授权”不能只根据是否存在角色判断，而应根据账号在当前目标租户内是否拥有实际有效菜单判断：

- `authorized`：至少拥有一个当前可用的有效菜单。
- `pending`：没有任何当前可用的有效菜单。
- `null`：本地账号不参与联邦账号授权状态。

部门为空不影响授权状态。账号启停状态继续由现有状态字段表达，不与授权状态混用。

### 2.3 非目标

- 不建设中控到业务系统的部门同步。
- 不建设中控到业务系统的角色或权限同步。
- 不增加自动轮询、自动默认授权或单独的待授权账号页面。
- 不改变未启用 SSO 项目的登录、用户管理和权限行为。

## 3. 总体流程

1. 用户从中控启动已获准访问的业务系统。
2. 目标系统兑换启动码，并按现有 JIT 流程创建或更新联邦影子账号及租户成员关系。
3. 目标系统按照实际有效菜单判断授权状态。
4. 没有有效菜单时，用户进入等待授权页。
5. 目标系统管理员在现有“系统管理 → 用户管理”中筛选“统一登录 / 待授权”。
6. 管理员点击“去授权”，复用现有编辑用户抽屉，为账号选择本地部门、岗位和角色。
7. 用户在等待页点击“重新检查”。页面完整刷新会话、用户信息、菜单和动态路由。
8. 获得有效菜单后进入首页；仍无有效菜单则继续停留在等待页。

## 4. 后端设计

### 4.1 用户列表契约

扩展现有 `GET /system/user`，不新增平行接口。

查询参数新增：

- `auth_source=local|federated`
- `authorization_status=pending|authorized`

用户响应新增：

- `authorization_status: "pending" | "authorized" | null`

当指定 `authorization_status` 时，查询范围自然收敛为联邦账号。本地账号的该字段始终为 `null`。

### 4.2 有效菜单解析

抽取一个共享的有效菜单解析能力，避免当前用户登录结果和管理员列表状态采用两套规则。解析结果必须同时满足：

1. 菜单来自用户当前有效角色。
2. 菜单处于启用状态，并适用于 PC 客户端。
3. 菜单属于当前租户套餐允许范围。
4. 菜单通过当前 Assembly 的租户侧过滤。

平台全局身份和租户超级管理员仍遵循现有菜单解析规则；本功能只为联邦账号输出授权状态，不重新定义平台权限模型。

用户列表应批量解析当前查询范围的授权用户 ID，避免逐行加载角色、菜单和套餐造成 N+1 查询。`authorization_status` 条件必须在数据库分页前参与查询，保证总数和翻页准确。

### 4.3 联邦账号可编辑字段

目标系统管理员编辑联邦账号时：

- 可修改：`dept_id`、`position_ids`、`role_ids`，以及现有明确属于目标系统的非身份业务字段。
- 不可修改：账号、姓名、手机、邮箱、头像、密码登录配置和由中控同步的账号状态。

后端必须实施字段边界，不能仅依赖前端禁用输入框。提交未变化的只读字段可以兼容接受；试图改变这些字段时返回明确的 400 错误。普通本地账号继续使用原有更新逻辑。

### 4.4 权限与租户隔离

- 查询继续要求 `module_system:user:query`。
- 编辑和授权继续要求 `module_system:user:update`。
- 不新增中控权限码。
- 查询、状态计算和更新必须使用当前认证租户上下文，禁止通过查询参数或请求体越权指定其他租户。

## 5. 前端设计

### 5.1 用户管理

现有用户管理页增加：

- “账号来源”筛选：全部、本地账号、统一登录。
- “授权状态”筛选：全部、待授权、已授权。
- “账号来源”列：本地账号、统一登录。
- “授权状态”列：待授权、已授权；本地账号显示短横线。

统一登录且状态为 `pending` 的行显示“去授权”。按钮复用现有编辑用户抽屉、现有角色和部门选项加载、现有更新接口，不复制表单和校验逻辑。

编辑联邦账号时：

- 账号、姓名、手机、邮箱、头像和状态只读，并显示“由中控统一维护”。
- 隐藏或禁用密码相关操作。
- 部门、岗位和角色保持可编辑。

本地账号的新增和编辑界面保持现状。

### 5.2 等待授权页

等待页文案明确说明：账号已创建，但目标系统尚未授予有效菜单权限。页面给出管理员操作路径：“系统管理 → 用户管理 → 筛选待授权 → 去授权”。

页面显示当前用户姓名和可供管理员检索的账号，不展示手机、邮箱、令牌或其他敏感信息。

“重新检查”不轮询。点击后执行完整页面刷新，由现有应用启动和路由守卫重新获取会话、用户信息、有效菜单和动态路由。刷新后仍无权限时返回等待页，并保持清晰提示。

## 6. 异常与状态变化

- 角色存在但没有菜单：保持 `pending`。
- 角色菜单不在租户套餐中：保持 `pending`。
- 角色、菜单被禁用，或套餐权限被回收：下一次查询变为 `pending`。
- 管理员只分配部门或岗位：保持 `pending`。
- 重复点击“重新检查”：只产生一次普通页面刷新，不创建新账号、不重复兑换启动码。
- 联邦账号的中控同步字段被篡改：后端拒绝并返回明确错误。

## 7. 测试要求

### 7.1 后端

- 新建联邦账号默认返回 `pending`。
- 分配含有效菜单的角色后返回 `authorized`。
- 空角色、空菜单、禁用菜单、套餐未包含菜单均为 `pending`。
- `auth_source` 和 `authorization_status` 的筛选、总数与分页准确。
- 状态计算遵循租户隔离和套餐隔离。
- 联邦账号中控同步字段不可修改，本地部门、岗位和角色可修改。
- 普通本地账号原有创建、编辑、密码和授权测试保持通过。

### 7.2 前端

- 筛选参数、状态标签和“去授权”操作符合契约。
- 联邦账号只读字段与本地字段边界正确。
- 本地账号编辑行为无回归。
- 等待页“重新检查”触发完整刷新，不启动轮询。

### 7.3 集成与发布门禁

- 重跑中控、目标系统、Redis 和独立 PostgreSQL 双库的真实 SSO 闭环。
- 后端运行 Ruff 和全量 pytest。
- 前端运行 type-check、全量 Vitest 和生产构建。
- 本功能不需要数据库迁移。

## 8. 仓库与发布范围

能力首先实现于 FastapiAdmin 框架仓库，供所有启用中控 SSO Client 的业务系统复用。FastapiAdmin-Control 不增加部门同步或角色同步。实现按后端契约、前端交互和回归验证分提交，完成后不自动 push。
